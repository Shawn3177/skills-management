# Skill 适配提醒与多版本自动切换

## 背景

共享库里的 skill 并不都适合每个工具。有些只为 Claude Code 写（依赖它的工具名、hooks、`$ARGUMENTS` 等），启用到 Codex 后会降级或失效。也有些仓库同时提供了面向不同工具的版本（`.claude/skills/X` 与 `.agents/skills/X` 内容不同）。

目标：
1. 启用到某个工具前，静态检查 skill 是否适配，不适配时**提醒但不阻止**。
2. 从 GitHub 导入时识别仓库里的多版本；启用时**自动选用该工具的专属版本并提示**，详情页可手动改。
3. 规则表按全部 12 个工具设计，首批只调好 Claude Code 和 Codex。

## 已确认的决定

- 不适配：只提醒，保留"仍然启用"；可手动标注"已确认适配"，内容变了重新提醒。
- 有专属版本：自动切换 + 一句提示；不满意在详情页改。
- 规则表覆盖 12 个工具，首批规则只针对 `claude-code` 与 `codex`。

## 真实仓库抽查（2026-10-21）

用 GitHub code search 抽了约 40 个带 `.agents/skills` 或 `.codex` 的仓库，加上 `series.json` 里的已知仓库：

| 现象 | 例子 | 对设计的影响 |
|---|---|---|
| 同名 skill 在多个工具目录里，**内容完全相同** | `Actual-Chat/actual-chat`、`eclipse-glsp/glsp-theia-integration`、`ui-ux-pro-max-skill`（`.claude/skills` 与 `cli/assets/skills`） | 只是重复，不算多版本 |
| 同名 skill 在多个工具目录里，**内容不同** | `Automattic/wordpress-activitypub`（8 组）、`DexForce/EmbodiChain`（17 组）、`Kanevry/session-orchestrator`（53 组，`skills/`、`.agents/`、`.codex-plugin/`、`.cursor/` 四个版本） | 真正的多版本，需要识别 |
| 某个"版本"只是**指针** | Automattic 的 `.claude/skills/dev/SKILL.md` 只写一句 "Read `.agents/skills/dev/SKILL.md`"；Kanevry 的 `.cursor` 版写 "Canonical skill: `skills/autopilot/SKILL.md`" | 单独装进工具目录后指向的文件不存在，**必须识别并丢弃，改用它指向的那份** |
| 专属版本是**机器转换出来的** | Kanevry `.codex-plugin` 版有 `<!-- Generated by scripts/generate-codex-skills.mjs -->`，把 `model`、`user-invocable` 挪进了 `metadata:` | 这是最理想的情况，正好可以用 |
| 不在工具目录下的同名副本 | `examples/skills/cg`、`cli/assets/skills/*`、`template/` | 不当作某个工具的版本 |
| `agents/openai.yaml` | mattpocock、remotion 每个 skill 都有 | 只是 Codex 的界面元数据。`git-guardrails-claude-code` 也有，但它依赖 Claude Code hooks。**不能当作"适配 Codex"的证据** |

## 第一部分：适配检查（`compat.rs`）

### 数据结构

```rust
pub enum CompatLevel { Compatible, Degraded, Incompatible }

pub struct CompatFinding {
    pub rule_id: &'static str,
    pub level: CompatLevel,      // 这一条命中的严重程度
    pub file: String,            // 相对 skill 目录
    pub line: Option<usize>,
    pub excerpt: String,         // 命中行，截断到 ~120 字符
}

pub struct CompatReport {
    pub target_id: String,
    pub level: CompatLevel,      // 所有命中里最严重的
    pub declared: Option<String>,// frontmatter `compatibility` 原文
    pub findings: Vec<CompatFinding>,
    pub acknowledged: bool,      // 用户已标注适配且内容没变
}
```

### 规则表

每条规则写明"这个特征属于哪些工具"（`owners`）。目标工具不在 `owners` 里才算命中。以后给 OpenCode、Gemini CLI 等补规则，只改这张表。

| id | 检查位置 | 特征 | owners | 级别 |
|---|---|---|---|---|
| `declared` | frontmatter `compatibility` | 明确写了只支持某工具（如 "Claude Code only"），且没提到目标工具 | — | 不适配 |
| `wrapper` | SKILL.md 正文 | 正文很短（去掉 frontmatter 后 < 600 字符），并且指向 skill 目录外的另一个 `SKILL.md` | — | 不适配（所有工具） |
| `cc-hooks` | frontmatter / 正文 / 脚本 | frontmatter `hooks:`；正文或脚本写 `.claude/settings.json`、`${CLAUDE_PLUGIN_ROOT}` | claude-code | 不适配 |
| `cc-fork` | frontmatter | `context: fork` | claude-code | 不适配 |
| `cc-name` | 文件夹名 / `name` | 含 `claude-code` | claude-code | 降级（讲 Claude Code 的 skill 不一定用不了） |
| `cc-frontmatter` | frontmatter | `allowed-tools`、`model`、`agent`（`disable-model-invocation`、`user-invocable`、`argument-hint` 只影响 Claude Code 怎么调用、菜单怎么显示，不影响功能，不算。用真实的 75 个 skill 试过：算上它们会有 34 个报警，大多是噪音） | claude-code | 降级 |
| `cc-tools` | 正文 | 整词匹配 `TodoWrite`、`AskUserQuestion`、`Task tool`、`WebFetch`、`WebSearch`、`SlashCommand`、`NotebookEdit`、`ExitPlanMode` | claude-code | 降级 |
| `cc-args` | 正文 | `$ARGUMENTS`（`$1`…`$9` 和 shell 示例分不开，不检查） | claude-code | 降级 |
| `cc-paths` | 正文 / 脚本 | `CLAUDE.md`、`~/.claude/`、`.claude/skills`、`.claude/commands`、`.claude/agents` | claude-code | 降级 |
| `cx-tools` | 正文 | `apply_patch`、`update_plan`、`spawn_agent` | codex | 降级 |
| `cx-paths` | 正文 / 脚本 | `~/.codex/`、`.codex/skills`、`CODEX_HOME`（`AGENTS.md` 多个工具都认，不算） | codex | 降级 |

frontmatter 只看顶层字段：转换过的版本会把 Claude 专用字段挪到 `metadata:` 下面，这种不算。同一条规则、同一个词只记第一次出现；同一行已经命中更严重的规则（比如 `~/.claude/settings.json`），不再重复记。

扫描范围：`SKILL.md`，skill 目录下的 `*.md`（references），以及脚本（`*.sh *.py *.js *.mjs *.ts *.ps1`，只检查路径类规则）。最多读 200 个文件，单个文件超过 512 KB 跳过，避免卡住。

只提醒不阻止，所以规则宁可漏报，不要误报。例如 `Task` 必须带上 "tool" 才算命中，普通单词 "task" 不算。

### "已确认适配"

存放在 `~/.skills-manage/compat-acks.json`：

```json
{ "<library 文件夹名>": { "codex": "<SKILL.md 的 git blob id>" } }
```

blob id 和当前 SKILL.md 一致，就视为已确认。从 GitHub 更新后内容变了，会重新提醒。

### 接入点

- 新命令 `check_skill_compat(sourcePath, targetId) -> CompatReport`（详情页"查看全部"时用）和 `acknowledge_skill_compat(sourcePath, targetId)`（标记已确认适配，走写锁）。
- `ScannedSkill` 新增 `compat: Vec<{ targetId, level, count, first, acknowledged }>`，只给共享库里的 skill 计算，只列"可能不适配"的工具。12 个工具共用一次文件读取。
- 前端开关直接用扫描结果里的 `compat` 判断要不要提醒，不额外调用后端。级别是"降级"或"不适配"并且没确认过，就沿用现有的 `setNotice({ kind: "warning", actions })` 方式提示：
  - 文案："`pdf` 可能不适配 Codex：用到了 Claude Code 的 `TodoWrite`（SKILL.md 第 42 行）等 3 处。"
  - 按钮：**仍然启用**、**查看详情**。
- 添加技能时勾选了要启用的工具：先逐个调用 `check_skill_compat`，可能不适配的先不启用，最后合并成一次提醒（"其中 N 处可能不适配，暂未启用：x → Codex"），提供"仍然全部启用"。
- 编辑页保存时要开启的工具里有可能不适配的：先提醒，提供"仍然保存"和"查看详情"。
- 详情页：每个工具一段，列出命中项（文件、行号、摘录），并提供"标记为已确认适配"按钮。
- 后端 `set_skill_target_enabled` **不做拦截**，保持现在的行为。

## 第二部分：多版本识别与自动切换（`variants.rs`）

### 识别（纯函数，可单测）

输入：仓库里所有文件路径和内容哈希。不需要额外的网络请求，因为导入和更新时已经下载了整个仓库的 zip（`download_zipball`）。

1. 列出所有含 `SKILL.md` 的目录，按文件夹名分组。
2. 按路径前缀判断每个版本归属哪个工具：

   | 前缀 | 归属 |
   |---|---|
   | `.claude/skills/`、带 `.claude-plugin/` 的仓库里的 `skills/` | claude-code |
   | `.codex/skills/`、`.codex-plugin/skills/` | codex（优先） |
   | `.agents/skills/` | codex（次选，Codex 读这个目录） |
   | `.cursor/skills/`、`.gemini/skills/`、`.opencode/skills/`、`.qwen/skills/`、`.qoder/skills/`、`.codebuddy/skills/` | 对应工具 |
   | `.kiro/`、`.github/skills/`、`.agent/skills/` | 识别出来，但不是本 app 的目标工具，忽略 |
   | 其他（`skills/`、根目录、`examples/`、`template/`、`cli/assets/`…） | 未归属 |

3. 整个目录内容一样（目录下所有文件的哈希都相同）的版本合并成一个，不算多版本。
4. 指针识别：版本的 SKILL.md 符合规则表里 `wrapper` 的条件，并且指向的是同组里的另一个版本，就丢弃这个版本。这个工具改用被指向的那份。
5. 输出：`{ tool_id -> 仓库内子目录 }`，只包含"有专属版本、并且和用户导入的那份内容不同"的工具。

用户导入时选中的那个子目录，仍然作为默认版本放进共享库。

### 存储

- 默认版本：仍是 `library/<skill>/`，结构不变。
- 专属版本：`~/.skills-manage/variants/<library 文件夹名>/<tool-id>/`。放在共享库外面，这样 `copy_skill_dir`、skillpack 导出、scanner 都不会误把它当成独立的 skill。
- `.skills-manage-source.json` 新增可选字段，旧文件照样能读：

  ```json
  "variants": { "codex": ".agents/skills/dev" }
  ```

- 手动指定写在 `~/.skills-manage/variant-prefs.json`：`{ "<skill>": { "codex": "default" } }`。
- 从共享库移除一个 skill 时，它的 variants 目录也一起移进 trash。

### 启用

`targets::set_skill_target_enabled_with_options` 内部的流程：

1. 校验仍然针对共享库路径，`validate_library_source` 不变。
2. `effective_source = variants::source_for(library_path, target_id)`：先看手动指定，再看专属版本，都没有就用库里的默认版本。
3. 从 `effective_source` 复制。marker 的 `source_path` 仍然记共享库路径，现有的 `marker_matches` 逻辑因此全部继续有效。marker 新增 `variant: Option<String>`。
4. `TargetToggleResult` 新增 `variant: Option<String>`。前端据此提示："已为 Codex 使用仓库提供的 Codex 版本（`.agents/skills/dev`）"。
5. 如果最终用的是默认版本，照常走第一部分的适配检查。

### 必须一起改的两处

1. **`scanner::target_state`**：现在的兜底判断 `same_skill_content(skill_dir, &copy)` 是拿副本和库里的默认版本比。启用了专属版本后，内容本来就不同，会被误判成"冲突"。要改成和 `effective_source` 比。
2. **`github::apply_skill_update`**：用同一个 zip 把每个专属版本也解压到 staging，和默认版本一起换上，再执行 `refresh_managed_copies`（它也要改成用 `effective_source`）。仓库里某个专属版本不见了，就删掉对应的 variants 目录，并提示"仓库已不再提供 Codex 版本，改用默认版本"。

### 早先导入的 skill

识别只在导入和更新时运行。详情页加一个"检测其他版本"按钮，手动触发一次，需要下载一次 zip。

### PR 2 实际实现（2026-10-21）

和上面计划相比的取舍：

- **有没有专属版本，以磁盘为准。** 也就是 `variants/<skill>/<tool>/SKILL.md` 在不在。`source.json` 里的 `variants` 只用来显示来源路径和更新时比对。marker 不加 `variant` 字段，因为不需要。
- **读 zip 很省。** 第一遍只看文件名，找出同名、又在工具目录下的候选目录。第二遍只读这些候选目录和用户选中的目录，最多读 50 MB。
- **适配检查跟着版本走（计划里漏了的一点）。** 某个工具有专属版本时，这个工具的适配提醒按专属版本判断，"已确认适配"也按专属版本的 SKILL.md 记。
- **编辑名称和描述时，专属版本的 frontmatter 一起改。** 不然保存后 Codex 那份还是旧名字。
- **更新时专属版本一起换。** 换的时机在库里那份换完之后、刷新各工具副本之前，所以每个工具都拿到新版本。仓库不再提供某个工具的版本时，那个工具改回用主版本，更新结果里会写一句"Using the main version again for: Codex."。
- **识别失败不影响导入。** 导入或更新时专属版本读不出来，导入照常完成。更新时读不出来就保留原来的专属版本。
- **手动切换（`variant-prefs.json`）和"检测其他版本"按钮留到 PR 3。**

用真实仓库试过：

- `Kanevry/session-orchestrator` 的 `skills/autopilot`：识别出 Codex 版本 `.codex-plugin/skills/autopilot`，优先于通用的 `.agents` 版。`.cursor` 和 `.claude` 下的两份都是指针，被丢掉。
- `DexForce/EmbodiChain` 的 `.claude/skills/add-atomic-action`：识别出 Codex 版本 `.agents/skills/add-atomic-action`。

已知限制：

- **被 `export-ignore` 的目录看不到。** GitHub 生成 zip 时会跳过 `.gitattributes` 里标了 `export-ignore` 的目录，比如 `Automattic/wordpress-activitypub` 就把 `/.agents/`、`/.claude/` 标掉了。这种仓库里的专属版本识别不到，而且从这些目录导入本身就会失败，报"路径不存在"，这是 PR 2 之前就有的问题。要解决得改成用 git trees + blobs API 下载，单独处理。
- **用户导入的就是指针时不会自动纠正。** 比如直接导入 Automattic 的 `.claude/skills/dev` 那个指针，PR 2 不会自动换成它指向的那份。不过适配检查会把它标成"所有工具都不适配"。

## 测试

- Rust `compat`：每条规则至少一正一反（例如普通单词 "task" 不应命中 `cc-tools`）；`declared` 优先；扫描文件数和大小的上限生效。
- Rust `variants`：用上面抽到的真实结构做 fixture：
  - Automattic 指针结构，应丢弃 `.claude` 版、改用 `.agents` 版；
  - Kanevry 四个版本，Codex 应选 `.codex-plugin` 版，`.cursor` 的指针版应丢弃；
  - ui-ux-pro-max 的内容相同副本，应合并；
  - `examples/` 下的副本，不应算版本。
- Rust `targets` / `scanner` / `github`：启用专属版本后状态显示"已启用"而不是"冲突"；更新时专属版本一起刷新；专属版本在上游消失后回退到默认版本。
- 前端：启用"降级"级别的 skill 出现提醒，点"仍然启用"后才调用 `setTarget`；已确认适配的不再提醒；有专属版本时提示里出现版本路径。

## 风险

- 静态规则有误报和漏报。缓解：只提醒不阻止，提醒里给出具体行，并支持标注"已确认适配"。
- 工具的格式会变（比如 Codex 改了读取的目录）。缓解：规则表和前缀表集中放在一处，改起来只动一个文件。
- 专属版本放在共享库外面，skillpack 导出时 v1 不带上，导入别人的 skillpack 只得到默认版本。在文档里写明即可。
